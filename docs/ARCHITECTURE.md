# Архитектура Server Room Climate Controller

Дата: 2026-09-22. Версия проекта архитектуры: 0.1. Это проект, а не описание уже реализованного ПО. Неутверждённые эксплуатационные правила отмечены непосредственно в документе; предложения не заменяют их согласование.

## 1. Принципы и инварианты

1. Единственный путь изменения оборудования: Controller → TransactionEngine → CommandGateway → HA services.
2. Policy не вызывает HA, не читает часы самостоятельно и не содержит транспортных деталей.
3. На один комплект оборудования — один владелец команд и не более одной активной транзакции.
4. Для исходной установки подтверждено ac_hard_min=−5 °C: при Tout ≤ −5 °C любой запуск AC запрещён, включая аварийный резерв. Запуск AC допустим только при свежем доказанном Tout > ac_hard_min, разрешённом питании и подтверждённых C.dr=0 и выходе вентилятора=OFF.
5. Разрешение вентиляции допустимо только после подтверждённого OFF кондиционера. Для аварийной вентиляции дополнительно доказана достаточная разность температур.
6. Все проверки выполняются повторно непосредственно перед каждым включающим действием; снимок, по которому принято решение, может устареть во время перехода.
7. unknown, unavailable, stale и optimistic состояние не являются доказательством выключения.
8. При выключенной автоматике запрещены новые исполнительные команды, в том числе retry и команды восстановления. Наблюдение продолжается.
9. Успешный вызов сервиса не завершает переход: нужен соответствующий контракту readback.
10. Никаких неограниченных повторов, автоматического обхода блокировок и команд EPO.
11. Кондиционер используется только для охлаждения: разрешённые целевые команды — OFF, COOL и уставка охлаждения. SRCC не отправляет HEAT, AUTO или HEAT_COOL и не добавляет отопительную ветку стратегии. Наличие этих режимов у climate entity не делает их допустимыми командами SRCC.

SRCC обеспечивает порядок своих команд. Он не может гарантировать взаимное исключение оборудования при ручном пульте, сторонней автоматике, ошибочном readback или отказе HA. Для физической гарантии нужен аппаратный interlock. В документации не следует обещать невозможность одновременной работы только средствами HA.

Это план структуры: пустые Python-модули до этапа реализации не создаются.

Один ConfigEntry представляет одну серверную. Несколько записей допустимы только с непересекающимися исполнительными entities. Общие датчики температуры/UPS допустимы. Перекрывающийся C.dr или climate отклоняется. Поддержку нескольких записей можно отложить без изменения чистого ядра.

Предлагаемый тип manifest — `helper`: интеграция координирует существующие HA entities. Совместимая минимальная версия HA и точная схема manifest фиксируются при реализации и проверяются hassfest, без выдуманного ограничения версии на этапе архитектуры.

## 3. Контракты данных

### 3.1 Нормализованное значение

`Signal<T>` содержит value, quality, source_entity_id, source_attribute, unit, reported_at, measurement_at (если есть), observed_at, freshness_basis и reason.

Quality: VALID / UNKNOWN / UNAVAILABLE / STALE / INVALID / UNVERIFIED. Время получения в SRCC не делает измерение свежим. Булевы сигналы трёхзначные: TRUE / FALSE / UNKNOWN. Для температуры используются °C, для заряда проценты, для runtime секунды; конверсия выполняется до Policy.

`InputSnapshot` — неизменяемый согласованный снимок последней наблюдаемой информации: temperatures, ventilation, climate, power, feedback, snapshot_revision и monotonic_now. Согласованность снимка не означает одновременное физическое измерение всех датчиков; допустимый разброс времени задаётся контрактами.

### 3.2 Роли входных entities и fallback

Все назначенные роли имеют собственный max_age и политику unknown/unavailable. Обязательность настройки отличается от обязательности свежего значения для конкретного действия.

| Роль | Тип / обязательность | При отсутствии достоверного значения |
|---|---|---|
| Tin | sensor, температура; обязательна | Нет нового решения о включении по потребности, degraded; политика продолжающегося охлаждения — (требует согласования) |
| Tout | sensor, температура; обязательна | Нет нового запуска AC; эффективность вентиляции неизвестна, резерв не разрешается автоматически |
| vent_enable | number с 0/1 либо switch через профиль; обязательна | Нельзя доказать запрещение/разрешение вентиляции |
| vent_enable_readback | sensor/binary_sensor/attribute либо та же entity, если она публикует настоящий readback; обязательное доказательство | Запуск AC запрещён до C.dr=0 |
| vent_output | binary_sensor или нормализуемый sensor; обязательна | Запуск AC запрещён: выход OFF не доказан |
| vent_demand | binary_sensor/attribute; необязательна | Специфический диагноз отказа вентиляции отключён |
| climate | climate с COOL/OFF и температурой; обязательна | AC unavailable; это не доказательство OFF |
| ac_fault | binary_sensor/sensor/attribute; обязательное назначение источника при наличии в драйвере | Состояние здоровья неизвестно; запуск по выбранному профилю блокируется |
| ac_availability | встроенная availability плюс необязательный отдельный сигнал | Недоступность любого обязательного для профиля сигнала делает устройство недоступным для команды |
| ac_execution / actual_off | entity/attribute; роль доказательства обязательна, отдельная entity зависит от драйвера | Нет завершения соответствующей фазы; optimistic climate не заменяет обратную связь |
| ups_on_battery | binary_sensor либо отображение enum; обязательна | Питание UNKNOWN, сеть не считается присутствующей |
| ups_online | binary_sensor либо enum; обязательна | Сеть не считается доказанной даже при on_battery=false |
| ups_voltage | sensor напряжения; обязательна в конфигурации по ТЗ | degraded; не заменяет on_battery, не обязательно блокирует вентиляцию |
| ups_charge | sensor 0..100%; обязательна | На батарее бюджет UNKNOWN; применяется выбранная консервативная политика |
| ups_runtime | sensor времени; необязательна | Если не настроена — политика по заряду; если настроена и потеряна — отдельная деградация |
| airflow / fan_current | sensor/binary_sensor; необязательна | Не делать вывода о наличии потока; если сигнал назначен обязательным доказательством профиля, блокировать зависимый вывод |
| hardware_alarm | необязательный binary_sensor | Наблюдение и диагностика; команды аппаратной защиты отсутствуют |

Входные domain и схемы значений ограничиваются проверяемыми профилями адаптеров, а не произвольными шаблонами исполнения. Для enum явно задаются значения true/false/fault; неизвестная строка не преобразуется в false. Если поле обязательно назначить, но оно временно unavailable, конфигурацию можно сохранить для наблюдения; автоматика ограничивается runtime guards.

### 3.3 Свежесть

`last_changed` не годится как возраст неизменной температуры. `last_updated` также может не отражать повторную публикацию того же значения. `last_reported` сообщает о записи состояния в HA, но сам по себе не доказывает новый опрос физического прибора. Предпочтительны timestamp измерения или heartbeat исходной интеграции. Семантика HA описана в [документации last_reported](https://developers.home-assistant.io/blog/2024/03/20/state_reported_timestamp/).

Способ freshness — часть профиля входа. Для событийных устройств требуется отдельное подтверждение живости, а не бесконечное доверие неизменному state. При отсутствии проверяемой живости роль получает UNVERIFIED; допустимость автоматического управления для неё должна быть явно определена. Ограниченная подписка на state_reported либо периодическая проверка last_reported учитывает ограничения API; не подписываться на все события HA.

Периодический watchdog необходим даже без событий: по истечении max_age он делает сигнал STALE и инициирует переоценку. restored state после старта сам по себе не проходит readiness.

### 3.4 Выход решения

`Decision`: desired_mode, reason_code, reason_params, blockers[], cooling_required, power_policy, constraints и evaluated_revision. `ControllerStatus`: observed_mode, committed_mode, lifecycle, severity, transition_phase, evidence, timers, last_success, last_error.

Коды причин стабильны и переводятся для UI; сырые сообщения исключений не становятся машинным API. Примеры: `AC_HARD_MIN_BLOCK`, `WAIT_VENT_OFF`, `WAIT_AC_OFF`, `WAIT_COMPRESSOR_GUARD`, `OUTDOOR_WOULD_HEAT_ROOM`, `POWER_UNKNOWN`, `INPUT_STALE`, `ACTUATOR_CONFLICT`.

## 4. Независимые машины состояний

### 4.1 Способ охлаждения

CoolingMode: IDLE / VENTILATION / AIR_CONDITIONING / EMERGENCY_VENTILATION / NO_COOLING_AVAILABLE.

- **IDLE:** подтверждённые AC OFF и C.dr=0; применяется при явном запросе остановки или иной согласованной политике. Отсутствие запроса холода от ТРМ в штатном режиме вентиляции не переводит SRCC в IDLE и не снимает C.dr=1.
- **VENTILATION:** AC доказанно OFF, C.dr=1. Фактический выход может быть OFF: им управляет ТРМ.
- **AIR_CONDITIONING:** C.dr=0, выход OFF, AC подтвердил режим COOL и уставку согласно контракту. Ожидание компрессора — диагностическая фаза, не отказ.
- **EMERGENCY_VENTILATION:** тот же исполнительный контракт, что VENTILATION, но другая причина и условия пригодности наружного воздуха.
- **NO_COOLING_AVAILABLE:** требуется охлаждение, но нет допустимого маршрута. Это решение стратегии; оно не означает, что оба устройства физически выключены.

`desired_mode` — выбранная цель; `committed_mode` — последний подтверждённый режим с отметкой времени. `observed_mode` может быть UNKNOWN или CONFLICT, если доказательств недостаточно либо обе системы разрешены. Эти значения не являются новыми способами охлаждения. Во время перехода нельзя выдавать предыдущий committed_mode за текущее достоверное состояние.

### 4.2 Lifecycle и переход

Lifecycle: STARTING → RECONCILING → RUNNING; боковые состояния PAUSED_MANUAL, DEGRADED, BLOCKED. Отдельно хранится фаза транзакции. Тем самым не требуется расширять CoolingMode значениями TRANSITION_TO_*.

DEGRADED не обязательно запрещает всё управление: каждое действие допускается по собственным guards. BLOCKED означает невозможность продолжить исполнительную транзакцию. Отключённая автоматика имеет приоритет над обоими состояниями.

### 4.3 Аварийность

Severity: NORMAL / WARNING / CRITICAL. Предложение: итог — максимум независимых причин температуры, качества данных, отсутствия охлаждения, конфликта и питания. Температурные пороги, выдержки и пороги выхода настраиваются; emergency ventilation сама по себе не означает CRITICAL.

Потеря Tin создаёт сигнал деградации, а не утверждение «температура нормальная». Уже установленную температурную CRITICAL нельзя снять по отсутствию данных; снятие требует свежего значения ниже порога восстановления. Назначение severity не отменяет AC_HARD_MIN, interlock и запрет команд при manual.

## 5. Алгоритм выбора

Исходная серверная не требует дополнительного обогрева: по наблюдению владельца тепловыделения стойки достаточно даже при Tout около −40 °C, а ТРМ-138 реже включает вентилятор. Уменьшение частоты включений при отсутствии запроса ТРМ — нормальное регулирование, а не отказ вентиляции. Это наблюдение не задаёт новый температурный порог SRCC. При низкой Tin контроллер не включает HEAT; low-temperature диагностика, если понадобится, согласуется отдельно. Обнаруженный внешний режим HEAT/AUTO/HEAT_COOL не считается OFF и не удовлетворяет условиям разрешения вентиляции; применяется существующая процедура reconciliation.

Штатная стратегия выбирает способ охлаждения по Tout, а ТРМ самостоятельно регулирует вентилятор по температуре помещения. Базовая граница предпочтения — 0 °C; фактические штатные переходы выполняются по согласованным порогам гистерезиса +1/−1 °C, описанным ниже. Отдельный порог Tin в SRCC не является условием штатного разрешения ТРМ. C.dr=1 не означает, что вентилятор обязательно включён.

Граница остаётся конфигурируемой с согласованным ориентиром 0 °C. Применение гистерезиса для защиты от дребезга согласовано. Пороги включают равенство: VENT → AC при Tout >= +1 °C, AC → VENT при Tout <= −1 °C. Временные выдержки ещё не утверждены. Ниже 0 °C штатно выбирается вентиляция; новый запуск кондиционера при отрицательной Tout допускается только как аварийный резерв и строго при Tout > AC_HARD_MIN. Порядок: качество входов → профиль штатной/аварийной работы и питания → выбор по Tout → доступность систем → выдержки → транзакция. Температурная необходимость отдельно учитывается в аварийном режиме и при работе от UPS. Guards проверяются повторно при исполнении.

| Условие | Кандидат |
|---|---|
| Tin недостоверна | Новые включения не планируются, degraded; работающая система по согласованной политике (требует согласования) |
| Подтверждённая штатная вентиляция, Tout < +1 °C, ТРМ не требует холода | VENTILATION: сохранить C.dr=1; выход вентилятора регулирует ТРМ |
| Работающий AC, Tout <= −1 °C, устройства исправны | VENTILATION; разрешение после подтверждённого AC OFF |
| Работающая вентиляция, Tout >= +1 °C | C.dr=0; при разрешённом и доступном AC — AIR_CONDITIONING |
| Вентиляция подозревается неэффективной, AC разрешён | AIR_CONDITIONING как резерв, в том числе при -5 < Tout < 0 |
| AC недоступен/заблокирован, Tin-Tout >= emergency_delta, вентиляция пригодна | Кандидат EMERGENCY_VENTILATION; запуск только после доказанного AC OFF |
| Наружный воздух не может отводить тепло и AC недоступен/заблокирован | NO_COOLING_AVAILABLE |
| Питание запрещает подходящий способ | NO_COOLING_AVAILABLE с причиной питания |

Для аварийной вентиляции обязательна полезная разность Tin−Tout; при Tout >= Tin резерв не допускается. Дополнительный порог Tin или delta не вводится в штатное разрешение ТРМ без отдельного решения. Неэффективность вентиляции запрещает бессмысленно выбирать её резервом снова без новых доказательств.

Гистерезис штатного выбора согласован для исходной установки:

| Подтверждённый режим | Условие по Tout | Следующий штатный режим |
|---|---|---|
| VENTILATION | Tout >= +1 °C | AIR_CONDITIONING после выдержек и подтверждения отключения вентиляции |
| AIR_CONDITIONING | Tout <= −1 °C | VENTILATION после выдержек и подтверждения AC OFF |
| Любой из этих двух | −1 °C < Tout < +1 °C | Сохранить текущий пригодный режим |

Параметры `vent_to_ac_temperature=+1 °C` и `ac_to_vent_temperature=−1 °C` остаются конфигурируемыми. Это уточняет базовую границу 0 °C: уже работающий AC может сохраняться между −1 и 0 °C, а разрешённая вентиляция — между 0 и +1 °C. Равенство верхнему/нижнему порогу запускает рассмотрение соответствующего перехода, но не отменяет выдержки и readback.

Гистерезис не разрешает новый штатный запуск AC при Tout < 0 °C и не обходит AC_HARD_MIN, interlock, неисправности, ограничения питания или качества данных. Удержание ранее подтверждённого AC в отрицательной части полосы отличается от нового запуска. Непригодный режим не удерживается только из-за нахождения в полосе. При старте без подтверждённого режима применяется отдельно согласуемое начальное правило; сохранённая старая команда не считается текущим режимом. Гистерезис не заменяет condition_hold и minimum_dwell.

Температура внутри стойки участвует в оценке достаточности охлаждения наряду с Tout. Предложение для согласования: при превышении допустимой температуры стойки и/или устойчивом росте при подтверждённой работе вентиляции формировать запрос резервного AC до достижения Tout=+1 °C. Для оценки вентиляции согласованы 5 минут наблюдения и 5 выборок с интервалом 1 минута; критерий значимого роста и необходимость отдельного температурного порога ещё согласуются. Резерв всё равно требует Tout > −5 °C, питания AC и подтверждённого отключения вентиляции. Если AC запрещён, перегрев стойки повышает аварийность и может приводить к NO_COOLING_AVAILABLE, но не снимает запрет.

Роль Tin в исходном ТЗ называлась температурой помещения; требуется уточнить, является ли датчик в стойке тем же Tin или отдельным входом `rack_temperature`. При разных датчиках не подменять их друг другом: явно назначить источник запроса охлаждения, тренда эффективности и аварийных порогов. Для автономного вентиляционного регулирования ТРМ подтверждены включение при 24 °C и выключение при 20 °C; эти уставки не являются порогами WARNING/CRITICAL. Допустимый температурный предел стойки и критерий значимого роста ещё согласуются. Обычное регулирование вентилятора по-прежнему остаётся у ТРМ, а не у SRCC.

Для аварийной/батарейной стратегии предлагается запрос охлаждения при Tin >= cooling_on и снятие при Tin <= cooling_off, где cooling_off < cooling_on; пороги и применение к AC ещё согласуются. Эти параметры не ограничивают штатное C.dr=1 при Tout < 0 °C. emergency_delta имеет отдельный порог выхода, который не может допустить вентиляцию при наружном воздухе теплее помещения.

`condition_hold` требует непрерывного сохранения кандидата; при исчезновении условия или потере качества сбрасывается. `minimum_dwell` отсчитывается от подтверждённого завершения режима. Эти таймеры задерживают оптимизационные переключения, но не блокируют останов по установленному запрету безопасности. Аварийный обход выдержек не обходит interlock или ограничения компрессора. Точная политика обхода — настраиваемая часть профиля.

При Tout=−2 °C и отказе вентиляции AC может быть резервом, если соблюдены питание, interlock и остальные guards. При Tout=−9 °C отказ вентиляции не разрешает AC: при необходимости охлаждения и отсутствии другого пригодного пути выбирается NO_COOLING_AVAILABLE с температурной/диагностической аварийностью. Точка Tout=−5 °C относится к запрету, а не к разрешению. Гистерезис предпочтения систем не может разрешить старт AC ниже или на hard-min. Поведение уже работающего AC при пересечении этой границы остаётся отдельным открытым решением.

## 6. UPS и питание

Подтверждённая схема исходной установки: кондиционер питается напрямую от сети; при пропадании сети его HA entity становится unavailable. При включённом кондиционере вентиляция ТРМ-138 должна быть заблокирована. Вентилятор и сам ТРМ-138 питаются от UPS; при пропадании сети сохраняется питание автономного регулятора и вентиляции. Взаимное исключение обязательно в обоих направлениях: при работе вентиляции кондиционер должен быть выключен; при работе кондиционера вентиляция должна быть заблокирована. AC на батарейное питание не переводится; при подтверждённом отсутствии сети запуск AC недоступен.

Отсутствие сети и потеря связи с AC должны различаться в диагностике. Чтобы использовать потерю питания как доказательство OFF для переключения, необходимо подтвердить соответствие сигнала UPS питающей линии AC, условия автоматического перезапуска Haier при возврате сети и порядок снятия разрешения вентиляции. Одно unavailable такого доказательства не даёт. При возврате питания AC может самостоятельно восстановить режим раньше HA; это требует проверки на стенде и при необходимости аппаратного interlock.

PowerState: MAINS / BATTERY / UNKNOWN / CONFLICT. Свежий on_battery=true означает BATTERY и исключает предположение о сети. MAINS требует on_battery=false и подтверждения online в смысле конкретного драйвера. Противоречие определяется картой значений: слово online у некоторых источников может означать доступность устройства, а не питание от сети.

Напряжение используется для диагностики и обнаружения несогласованности, но не отменяет on_battery. При конфликте выбирается консервативный профиль без предположения MAINS.

PowerPolicy — отдельная таблица допуска AC/вентиляции для MAINS, BATTERY_NORMAL, BATTERY_LOW, BATTERY_CRITICAL и UNKNOWN. Уровни батареи и runtime настраиваются; при обоих достоверных источниках берётся более ограничивающий бюджет. Отсутствующий необязательный runtime не равен нулю.

Для исходной установки AC при отсутствии сети недоступен независимо от заряда UPS; вентиляция разрешается только по запросу температуры, полезному delta и доступности её питания. Это не окончательное эксплуатационное правило. Поведение при низком заряде и при критической температуре задаётся явно; контроллер не придумывает компромисс сам.

Возврат сети имеет отдельную выдержку стабильности. Дребезг UPS не должен приводить к циклам AC. Изменение питания переоценивает и уже выполняемый переход перед следующим действием.

## 7. Транзакции

### 7.1 Модель

Transaction хранит id, generation, from/to, phase, started_at, deadlines, expected_predicate, evidence_baseline, command_intent, attempts, config_revision и failure. Все запросы проходят одну очередь контроллера. Перед выдачей команды проверяются automatic_enabled, актуальная generation, конфигурация и guards.

Команда идемпотентна только при явной установке состояния (`0`, `1`, `OFF`, `COOL`, конкретная температура). `toggle` запрещён. Сходный повтор не считается безопасным автоматически: нужны свежие guards и readback. Предлагаемая политика до согласования — ноль автоматических повторов. Позже retry допускается лишь для внесённых в allowlist операций с ограничением числа попыток.

Журнал намерения записывается перед командой, результат и доказательство — после. Сервис и запись журнала не образуют атомарную операцию: exactly-once не обещается. После сбоя неопределённый результат разрешается чтением оборудования, а не воспроизведением журнала.

### 7.2 Вентиляция → AC

1. Проверить устойчивый кандидат, dwell, питание, Tout и состояние допуска.
2. Записать intent; отправить C.dr=0, если это состояние ещё не доказано.
3. `WAIT_VENT_DISABLED`: дождаться C.dr=0 по достоверному readback.
4. `WAIT_VENT_OUTPUT_OFF`: дождаться отдельного выхода OFF. Ни одна из двух проверок не заменяет другую.
5. Повторить все guards, включая свежесть Tin/Tout и UPS.
6. Установить ac_target_temperature без неявного включения, если профиль это гарантирует; подтвердить уставку. Если поддержан только общий вызов COOL+temperature, использовать согласованный профиль общей команды.
7. Отправить COOL. Дождаться подтверждения команды, режима и уставки.
8. Зафиксировать AIR_CONDITIONING после достаточного readback. При задержке компрессора показывать WAIT_COMPRESSOR_GUARD; контроль эффективности ещё не активен.

Если состояние COOL в исходной интеграции optimistic, шаг 8 требует дополнительного фактического подтверждения. Если контракт требует доказательства работы компрессора, переход остаётся в ожидании с отдельным startup deadline, учитывающим защиту; обычный readback timeout не используется как время запуска компрессора.

### 7.3 AC → вентиляция

1. Проверить кандидата и разрешение вентиляции.
2. Отправить OFF, если физический OFF ещё не доказан.
3. `WAIT_AC_OFF`: подтвердить выключение по профилю. Недоступность, fault или hvac_action=idle при COOL не удовлетворяют условию.
4. Снова проверить качество данных, пригодность воздуха, питание и отсутствие запрета.
5. Отправить C.dr=1.
6. `WAIT_VENT_ENABLED`: подтвердить readback=1.
7. Зафиксировать VENTILATION или EMERGENCY_VENTILATION. Не ждать обязательного ON вентилятора: его решает ТРМ.

При подтверждённом аппаратном снятии питания AC профиль может использовать это как доказательство OFF, но отсутствие связи или сетевого напряжения само по себе таким доказательством не является.

### 7.4 IDLE, ошибка, потеря условий

Переход в IDLE подтверждает AC OFF и C.dr=0/выход OFF. При невозможности подтвердить одну часть состояние остаётся UNKNOWN/BLOCKED, а не ложно IDLE. NO_COOLING_AVAILABLE не является командой «всё выключить»: отдельный план учитывает известное фактическое состояние и согласованную политику остановки.

При timeout фиксируются команда, ожидание, доказательства и причина. Включение второго устройства блокируется. Автоматического отката к прежнему включённому режиму нет: новый маршрут строится по свежему snapshot.

Если цель меняется в середине перехода, generation устаревает, дальнейшие включения старого плана запрещаются. Уже выполненные отключения остаются фактом; reconciliation выбирает новый маршрут. Если теряется связь после отправки COOL, результат считается неопределённым, вентиляция не включается.

Отключение automatic_enabled отменяет таймеры исполнения и запрещает следующую команду, в том числе OFF. Уже доставленную оборудованию команду отозвать нельзя; это показывается как pending/unresolved. При последующем включении — reconciliation, а не продолжение старого плана.

## 8. Неэффективность и восстановление здоровья

HealthEvaluator ведёт отдельные окна Tin для каждого подтверждённого режима. При смене режима, пропуске данных или смене конфигурации окно сбрасывается. Используется тренд по нескольким измерениям с минимальным числом точек, допустимым разрывом, минимальным ростом и длительностью. Не выводить отказ по двум соседним отсчётам.

Для AC отсчёт оценки начинается после подтверждения запуска/начала охлаждения и startup grace, покрывающего нормальную защиту компрессора. Command timeout, fault, unavailable и thermal_ineffective — разные причины. Статус ожидания компрессора не является отказом. Бесконечно ждать защиту нельзя: отдельный согласованный startup deadline даёт `start_unconfirmed`, а не необоснованный диагноз поломки компрессора.

Для вентиляции специфическое подозрение требует C.dr=1, demand=true, output=ON и устойчивого роста Tin на заданном окне. Если demand отсутствует, возможна только общая диагностика недостаточного охлаждения, явно менее достоверная. Airflow/current усиливают доказательства по заданному профилю.

### Окно оценки вентиляции

Согласованы `vent_observation_duration=300 s`, `vent_sample_interval=60 s`, `vent_sample_count=5`; параметры остаются настраиваемыми. Автономные уставки ТРМ: включить вентилятор при Tin >= 24 °C, выключить при Tin <= 20 °C, между уставками сохранить состояние. SRCC не воспроизводит это регулирование сервисными командами.

Предлагаемая точная привязка времени: t0 — подтверждённый переход выхода вентилятора в ON при C.dr=1; пять выборок на t0+60, +120, +180, +240 и +300 секунд. Первая оценка — через полные 5 минут работы, а не через 4. Пять точек расположены на интервале 4 минуты внутри пяти минут наблюдения; значение в t0 можно хранить отдельно как начальное диагностическое, не называя его одной из пяти выборок. Это явно отличает время работы вентиляции от интервала между первой и последней точкой тренда.

В течение окна необходимы подтверждённые C.dr=1 и выход ON. При OFF выхода, потере качества данных, смене режима или конфигурации окно сбрасывается. Повторное включение начинает новый период. Если SRCC запускается при уже включённом вентиляторе, неизвестная предыстория не засчитывается: наблюдение начинается после readiness. Пропущенные точки не восстанавливаются повторением предыдущего значения.

Каждая выборка — свежие данные исходной HA entity, а не прямой опрос ТРМ. Нужен контракт обновления, позволяющий отличить новое неизменное измерение от старого кэшированного значения. Публикация того же числа допустима при подтверждённой свежести; пять чтений одного старого state не являются пятью измерениями. Требуемую частоту публикации обеспечивает интеграция устройства.

Для вычисления динамики предлагается линейный тренд по фактическим временам пяти точек с выводом скорости °C/мин и суммарного изменения. Положительный наклон сам по себе не должен объявлять неэффективность: требуется согласовать минимально значимый рост с учётом разрешения и шума датчика. До согласования этого критерия алгоритм может показывать динамику, но автоматический резервный переход по ней не считается полностью определённым. Пять значений помогают оценить достаточность охлаждения, но не доказывают конкретную механическую неисправность вентилятора.

Если выход остаётся ON, после первой оценки предлагается пересчитывать динамику каждую минуту по последним пяти свежим точкам; первый результат по-прежнему не ранее t0+300 секунд. Это предложение о скользящем окне требует согласования вместе с критерием тренда. Температурные WARNING/CRITICAL оцениваются независимо и не ждут окончания этого окна. К AC данное пяти минутное окно автоматически не применяется: его startup grace и диагностика согласуются отдельно.

Восстановление требует выдержки достоверного нормального состояния. Сброс ошибки оператором очищает latch/историю, но не меняет реальные fault/unavailable и не снимает hard guards. Автоматические пробные запуски после отказа не входят в первую версию без отдельной политики.

## 9. Запуск, хранение и останов

1. Загрузить и проверить схему ConfigEntry, options и версию Store.
2. Подписаться на назначенные входы, собрать свежий snapshot; до reconciliation команд нет.
3. Ждать обязательные для допуска сигналы до startup_timeout. Неназначенные опциональные сигналы не задерживают старт.
4. Если срок истёк — отобразить конкретные отсутствующие роли; продолжать наблюдение в degraded/blocked. Не объявлять готовность и не бесконечно прятать причину за STARTING.
5. Сопоставить оборудование с последним режимом/транзакцией. Сохранённый режим — подсказка, текущие доказательства приоритетны.
6. Если цель уже физически достигнута — признать подтверждённый режим. Если предыдущая система OFF, а новая не запущена — заново вычислить цель. Если старое состояние не определено — блокировать встречное включение.
7. При конфликте двух разрешённых систем — диагностика и предлагаемый план последовательного отключения, только если автоматическое управление разрешено и утверждена recovery policy. Иначе пауза для оператора; никакого заявления, что конфликт устранён.
8. Начать автоматическое управление только после readiness и проверки настроек; сохранённое false всегда сохраняет manual.

Store содержит schema_version, намерение automatic_enabled, подтверждённый режим и timestamp, транзакционный intent, latch ошибок и последнее успешное действие. Не хранить текущие входы как источник истины. Исторические тренды можно отбросить; после старта собирается новое окно.

Длительности в живом процессе считаются по монотонным часам; UTC применяется для журнала. После рестарта condition_hold начинается заново, а dwell/restart guard восстанавливаются консервативно при сомнительном времени. Простой HA не считается доказанным периодом остановки компрессора.

Unload снимает подписки, отменяет задачи/таймеры, запрещает команды, сохраняет нужное состояние. Остановка HA не должна запускать неподтверждаемую цепочку выключения.

## 10. Home Assistant API и конфигурация

Config Flow: идентификация помещения → входные роли → профили readback и питания → параметры стратегии → проверка готовности. Options Flow — эксплуатационные пороги и задержки; Reconfigure — переназначение источников. Изменение конфигурации инвалидирует текущую generation и требует reconciliation.

HA поддерживает UI-настройку через Config Flow и отдельный шаг reconfigure; см. [Config flow](https://developers.home-assistant.io/docs/core/integration/config_flow/). Реализация должна соответствовать выбранной минимальной версии HA, а не копировать изменяемые примеры без тестов.

Runtime объекта контроллера хранится в `ConfigEntry.runtime_data`; подписки — на назначенные entity IDs через `async_track_state_change_event`. Отдельный watchdog обслуживает возраст и deadlines. Подход к подпискам описан в [Listening for events](https://developers.home-assistant.io/docs/integration_listen_events/). Полноценный DataUpdateCoordinator не обязателен: собственных сетевых опросов нет, контроллер публикует единый immutable Status подписчикам платформ.

Сервисы HA: `number.set_value`/`switch.turn_on`/`switch.turn_off` для выбранного профиля разрешения; `climate.set_hvac_mode` и `climate.set_temperature` для AC. Наличие COOL/OFF, возможности задания температуры и семантика исполнения проверяются по конкретной entity. Возможности различаются между climate платформами: [Climate](https://www.home-assistant.io/integrations/climate/).

Валидация: корректный domain и значения; единицы и finite числа; диапазон/шаг number для 0/1; климатические режимы и диапазон уставки; отсутствие назначения выходов SRCC собственными входами; отсутствие пересечения приводов разных ConfigEntry; cooling_off < cooling_on; warning < critical; пороги восстановления ниже порогов входа; ac_hard_min < normal_ventilation_limit; положительный emergency_delta; неотрицательные выдержки, положительные deadlines/max_age; согласованные окна диагностики и compressor grace. Несовместимый профиль отклоняется с понятной причиной.

Доступ к HA service из Config Flow для проверки не нужен: настройка не запускает оборудование. Проверяется контракт и доступная метаинформация; физические возможности подтверждаются отдельными стендовыми сценариями.

## 11. Наблюдаемость и сервисы

Sensor: operating/observed mode, desired mode, decision reason, transition phase, severity, Tin/Tout/delta, condition timer, dwell, last_success, last_error. В attributes — reason_code, blockers, возраст данных, фаза, дедлайн и доказательства. Таймеров несколько: атрибуты именованы, а не смешаны в единственное число.

Binary sensor: cooling_required, ventilation_allowed/effective, ac_allowed/available/failure_suspected, mains_failure, ups_low, no_cooling_available, controller_degraded. Неизвестное значение публикуется как unknown/unavailable по контракту платформы, а не false. ventilation_allowed отражает доказанный C.dr, а ventilation_effective — оценку с указанием confidence/оснований.

Switch automatic_control_enabled: включение проверяет готовность и начинает reconciliation; выключение прекращает выдачу команд. Наблюдение и диагностика продолжаются.

Предлагаемые сервисы с target entry:

- `reevaluate`: перерасчёт; не обходит guards и manual.
- `request_idle`: подтверждаемый запрос отключения обоих исполнительных механизмов при включённой автоматике; в manual отклоняется. Название «safe» не используется без согласованной модели безопасности.
- `reset_diagnostic_error`: сброс диагностической фиксации без подмены реального здоровья.
- `pause_automation`: выключение автоматики; необязательная длительность. Если поддержан auto-resume, он сохраняется и проходит readiness заново; политика должна быть явной.
- Диагностический отчёт через `diagnostics.py`; отдельный сервис добавлять только при необходимости service response.

Журналирует переходы, причины отказа и успешные действия, ограничивает повторы одинаковых предупреждений. Диагностика содержит версию схемы, параметры, quality, snapshot, transition и capabilities, с редактированием идентификаторов и без случайного экспорта посторонних HA attributes. Никаких force-start сервисов.

## 12. Решения первого этапа

Принять как основу реализации: независимое чистое ядро; последовательный исполнитель транзакций; доказательства вместо успеха service; отдельные mode/severity/lifecycle; watchdog свежести; versioned журнал; manual как абсолютный запрет новых команд.

Оставить открытыми до ввода в эксплуатацию: числовые настройки, энергетическую политику, семантику IDLE, останов работающего AC по hard-min, потерю Tin/Tout, точные доказательства readback и retry. Реализация режима наблюдения может начаться без опасных значений по умолчанию.

## 13. Независимая аппаратная защита исходной установки

По описанию владельца на объекте установлен отдельный контроллер системы автоматического пожаротушения с баллоном Хладона, не зависящий от серверной стойки. Его температурный датчик расположен в наиболее тёплой точке стойки. При температуре >=30 °C контроллер задействует EPO UPS и отключает вводной автомат серверной стойки. Датчики дыма также инициируют отключение питания и выпуск огнетушащего вещества в защищаемый объект.

Температурное отключение и запуск пожаротушения по дыму описываются раздельно: из предоставленной информации не следует, что достижение 30 °C само по себе запускает выпуск вещества. Это описание существующей системы владельцем, а не результат проверки её схемы, автономности или сертификации в рамках SRCC.

Порог 30 °C принадлежит внешней аппаратной защите. SRCC его не изменяет, не отменяет EPO, не восстанавливает питание стойки и не управляет выпуском вещества. Аппаратная защита должна оставаться независимой от доступности HA. При наличии доступных сигналов интеграция может наблюдать состояние защиты и показывать его оператору; отсутствие интеграции сигналов не препятствует автономной работе аппаратного контура.

Порог аппаратного отключения не следует автоматически назначать порогом software CRITICAL: предупреждение климатической автоматики необходимо согласовать ниже него с учётом расположения датчиков, их расхождения и скорости нагрева. Числа WARNING/CRITICAL пока не назначены. Пять минут оценки эффективности вентиляции не задерживают температурную аварийную индикацию и никак не задерживают аппаратный EPO. Решение о досрочном резервном переходе при высокой температуре требует отдельного правила; оно не может обходить AC_HARD_MIN и взаимное исключение исполнительных систем.

Не считать температуру датчика ТРМ равной температуре самой тёплой точки без проверки их размещения. Для настройки программных порогов требуется уточнить, расположены ли эти датчики рядом и какова наблюдаемая разница показаний. Не предполагать, что EPO UPS оставляет питание вентилятора, ТРМ или HA: область отключения и доступные после срабатывания сигналы ещё не описаны. Автоматический повторный запуск после аппаратного срабатывания в SRCC не проектируется без отдельного согласования.
