# Разработка ядра SRCC

## Реализованный этап

Код в `custom_components/fourvrs_server_room/core/` представляет независимое от Home Assistant ядро. Его можно запускать без оборудования, внешних библиотек и сетевых подключений. Добавлен HA-слой наблюдения: manifest, Config Flow/options, 11 sensors, 4 binary sensors, нормализация входов, диагностика и очистка подписок. Ручная установка описана в INSTALLATION.md. Исполнитель сервисов и сохранение состояния остаются следующим этапом; команд устройствам нет.

| Модуль | Реализованное поведение |
|---|---|
| models | Неизменяемые снимки, качество/возраст данных, режимы, согласованные настройки и валидация |
| inputs | Основной ТРМ; при его отказе среднее двух достоверных «Болид» или единственный достоверный датчик с предупреждением |
| severity | WARNING от 26 °C; CRITICAL от 28 °C; снятие температурной CRITICAL после двух минут <=27 °C со снижением |
| health | Пять свежих измерений на минутах 1–5 после включения вентилятора; дальнейшее скользящее окно, тренд °C/мин |
| policy | Штатный гистерезис +1/−1 °C, резервные кандидаты, hard-min −5 °C, явные причины ограничения |
| timing | Непрерывная выдержка кандидата и dwell от подтверждения режима; длительности задаются явно |
| transitions | Последовательный план намерений OFF/C.dr/уставка/COOL, readback, timeout, ручная пауза и блокировка после ошибки |
| controller | Режим наблюдения Observer: источник температуры → аварийность → тренд → желаемый режим |

`TransitionPlanner` возвращает намерения, не выполняет команды. Будущий HA-исполнитель должен сериализовать планирование и отправку, повторно проверить допуск непосредственно перед сервисом, журналировать intent и вызвать fail при ошибке. Успех сервиса не считается подтверждением; ядро ждёт более нового фактического readback.

## Локальная проверка

Из корня репозитория, Python 3.11 или новее:

```shell
python -m unittest discover -s tests -v
python -m examples.temperature_recovery
```

Первая команда проверяет поведение на искусственных последовательностях событий. Вторая показывает NORMAL → WARNING → CRITICAL → восстановление. Они не обращаются к Home Assistant и не запускают оборудование. Совместимость с конкретной версией HA этими тестами не подтверждается.

## Настройки и пока не реализованные правила

- Согласованные числа входят в `Config`, но остаются изменяемыми параметрами. WARNING=26 °C реализован пока как непосредственный порог без отдельной задержки/гистерезиса; политику его восстановления можно расширить после согласования.
- Минимально значимый рост вентиляционной температуры не задан. Без `minimum_vent_rise` ядро показывает тренд, но не объявляет вентиляцию неэффективной автоматически.
- Снижение для снятия CRITICAL проверяется отрицательным общим трендом и конечной температурой ниже начальной. Дополнительный ненулевой запас от шума не согласован; предусмотрен параметр `minimum_recovery_drop`.
- `emergency_delta`, max_age, допустимое рассогласование времени резервных датчиков, sampling tolerance, readback timeout, уставка AC, condition_hold и minimum_dwell задаются явно для выбранного контракта. Числа в тестах — тестовые данные, не эксплуатационные настройки.
- При батарее/неизвестном питании ядро возвращает `POWER_POLICY_REQUIRED`: пороги бюджета UPS и действия при них ещё не согласованы. Ни AC, ни вентилятор автоматически не запускаются этим результатом.
- При холодном старте внутри полосы гистерезиса возвращается `INITIAL_MODE_POLICY_REQUIRED`; фактический режим должен установить будущий reconciliation.
- Смена основного/резервного источника сбрасывает тренд. Критическая температура оценивается немедленно, без ожидания нового окна. Задержка возврата на восстановившийся ТРМ пока не реализована: чистый селектор выбирает свежий ТРМ сразу.
- HA-адаптер читает состояния, переводит единицы и фиксирует отображение last_reported в монотонное время. Публикации не считаются доказательством физического readback. Проверка heartbeat конкретных интеграций и исполнительных возможностей climate ещё не завершена.
- Оценка отказа самого кондиционера, компрессорная защита, журнал незавершённых транзакций и восстановление HA ещё не реализованы. Данные `ac_ineffective` и доступность пока поставляет вызывающая сторона.

## Резервные датчики

В исходной установке предусмотрены две роли «Болид». При исправном ТРМ их температура не участвует в штатной стратегии. При отказе основного датчика:

1. Два достоверных показания: среднее арифметическое, без выбора максимума.
2. Одно достоверное: его значение и отдельное предупреждение `BACKUP_UNAVAILABLE` с идентификатором проблемного источника; итоговая severity не ниже WARNING.
3. Ни одного достоверного: температура неизвестна; сохранённая CRITICAL не снимается.

Свежесть среднего определяется более старым измерением. Время расчёта среднего не обновляет возраст входов. Переход «среднее → один → среднее» меняет идентификатор источника и не может выглядеть как физическое охлаждение одного датчика.

Недоступность данных в SRCC не означает физическую неисправность всех датчиков: возможна потеря связи или HA-представления. Автономные функции пожарного контроллера от этой модели не зависят.

## Проверки HA

Для локально доступного образа `ghcr.io/home-assistant/hassfest:latest` (на момент проверки: HA 2026.9.2, Python 3.14.5) из PowerShell в корне репозитория:

```powershell
docker run --rm --network none --mount "type=bind,source=$($PWD.Path),target=/repo" -e PYTHONPATH=/repo:/usr/src/homeassistant --workdir /repo --entrypoint python ghcr.io/home-assistant/hassfest:latest -m unittest discover -s tests/ha -v
docker run --rm --network none --mount "type=bind,source=$($PWD.Path),target=/github/workspace,readonly" ghcr.io/home-assistant/hassfest:latest
```

Тесты HA создают временную конфигурацию внутри `.local/` и не подключаются к рабочему экземпляру. Образ hassfest содержит исходный код HA и необходимые для этих тестов библиотеки; содержимое тега latest может измениться. Интеграционные проверки используют реальные состояния, события, Config Flow, реестры и загрузчик платформ. Отдельный lifecycle-тест подменяет forwarding для изоляции; полный тест дополнительно создаёт все 15 entities без этой подмены, проверяет options/reload/unload. Валидация hassfest выполняется без сети.

Физический readback, поведение приборов, история CRITICAL после рестарта и исполнительные сервисы этими проверками не подтверждены.
