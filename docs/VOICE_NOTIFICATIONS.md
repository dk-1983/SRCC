# Подготовка голосовых оповещений SRCC 0.4.0

SRCC остаётся самостоятельным контроллером охлаждения. Один config entry содержит один процесс `climate`, координирующий AC и вентиляцию. Отдельные источники для ТРМ, вентилятора, Haier или каждого резервного датчика не создаются. Оборудование берётся из существующих настроек SRCC.

**Статус: подготовлена клиентская сторона. Home Control 0.11.0 не реализует внешний контракт.** При её отсутствии SRCC показывает в диагностике `voice.connection: center_unavailable`; управление серверной работает независимо. Ни колонки, ни центр автоматически не включаются. Полная спецификация для отдельной реализации приёмника — [VOICE_PROTOCOL_V1.md](VOICE_PROTOCOL_V1.md).

## Настройки процесса

В существующей форме настройки SRCC добавлены одинаковые ключи с подписями RU/EN:

| Ключ | Подпись RU | Назначение и значение по умолчанию |
|---|---|---|
| voice_area | Помещение оповещений | Помещение HA; если пусто — помещение устройства самого SRCC |
| voice_info | Голосовые сообщения INFO | Одноразовые сообщения о завершённом изменении режима/восстановлении; OFF |
| voice_warning | Голосовые предупреждения WARNING | Деградация данных, резервное питание, отложенное действие; OFF |
| voice_error | Голосовые ошибки ERROR | Подтверждённые процессом тревоги и ошибки; OFF |
| voice_repeat | Повторять активные ERROR через центр | Разрешение напоминаний центра; OFF; без voice_error повторов нет |

Отдельный переключатель **«Обслуживание оповещений (охлаждение не изменяется)» / Notification maintenance (cooling unchanged)** сохраняется в HA Store. ON запрещает новые уведомления процесса, очищает локальные ещё не отправленные INFO и передаёт центру отмену ожидающих сообщений и напоминаний. После перезапуска режим сохраняется; при ошибке чтения его хранилища оповещения остаются выключенными.

Этот переключатель **не меняет Automatic control, режим AC, уставку, C.dr, ВУ или приоритеты охлаждения**. Выключение Automatic control и обслуживание оповещений — разные действия: температурный мониторинг остаётся полезным и при ручном управлении оборудованием. При выходе из обслуживания передаются только актуальные проблемы, без речи о старых переходах. Уже отправленную колонке речь SRCC остановить не может; при недоступном центре отмену ограничивает lease на стороне центра.

Параметров колонок, громкости, ночных интервалов, присутствия, дедупликации или времени напоминания в SRCC нет. INFO маршрутизирует центр в помещение процесса/альтернативу по присутствию; WARNING и ERROR — на все настроенные доступные колонки центра.

## Таблица смысловых событий

Таблица соответствует `voice_events.py`, `core/controller.py`, `core/severity.py`, `core/policy.py` и `execution.py`. Новых температурных или аварийных порогов не добавлено. Тексты намеренно не содержат меняющуюся каждую секунду температуру, остаток таймера или аппаратный entity_id.

| Стабильный key | Уровень и условие | Когда снимается |
|---|---|---|
| temperature_high | WARNING при существующем TEMPERATURE_WARNING; ERROR при защёлке thermal_critical | По текущему решению TemperatureAlarm, включая его прежнюю выдержку снижения; потеря температуры сама не снимает прежнюю тревогу |
| input_quality | WARNING при любом настроенном входе с качеством не valid либо status.degraded, в том числе резервном температурном источнике | Все учитываемые входы вновь valid и деградация снята |
| ac_fault | ERROR только при достоверном snapshot.ac_fault=true | Достоверный false; unknown не доказывает восстановление |
| ventilation_ineffective | ERROR при существующем vent_failed, который выставляется температурным трендом SRCC | Сброс признака самим контроллером; это не утверждение о ремонте вентилятора |
| execution_failure | ERROR при зафиксированном executor.error | Сброс ошибки контроллером при новом согласовании; это не доказательство физического ремонта |
| equipment_conflict | ERROR при reported_mode=conflict по обратной связи HA | Достоверный непротиворечивый reported_mode; unknown не считается восстановлением |
| power_supply | WARNING при Power.BATTERY или Power.UNKNOWN | Power.MAINS |
| cooling_unavailable | WARNING при решении NO_COOLING_AVAILABLE | Контроллер принимает другое определённое решение; desired=None не доказывает снятие |
| action_deferred | WARNING при включённом Automatic control и WAIT_TIMING, WAIT_AC_MINIMUM_OFF, WAIT_HAIER_COMMAND или BLOCKED | Этап исполнения выходит из этих состояний; отдельное recovery INFO не отправляется |
| mode_changed | Одноразовый INFO после подтверждённой команды и COMPLETE, когда установленный режим изменился либо выполнен ac_cool | Не активная проблема; начальное чтение и промежуточное отключение при переходе не озвучиваются |
| key восстановленной проблемы | Сначала explicit resolved, затем одноразовый INFO с тем же key, если voice_info включён | Новая активная проблема с тем же key заменяет ожидающее сообщение о восстановлении |

Режимы в INFO: кондиционирование, автоматическая вентиляция, подтверждённая резервная вентиляция или отключение активного охлаждения. Коррекция только числовой уставки не создаёт mode_changed. Успешный вызов сервиса без readback не считается завершением команды. Ошибка ожидания readback озвучивается как ошибка процесса, а не как доказанная поломка кондиционера.

Тексты речи этой версии русские, как у текущего центра; названия настроек и переключателя локализованы RU/EN.

Проекция сверяет существующее состояние SRCC; она не опрашивает оборудование. Неизменные проблемы не публикуются каждую секунду, регистрационный heartbeat передаёт лишь snapshot. Для коротких повторов, очереди и акустических напоминаний действует дедупликация Home Control. Повторное чтение одного датчика само по себе речи не создаёт.

## Разделение ответственности и перезапуски

`voice_events.py` строит смысловые события, `voice.py` обслуживает исключительно публичные services/events согласованного контракта. Исполнение оборудования не ожидает ответа центра. Сервис имеет локальный предел ожидания 3 s, при ошибке следующий запрос ограничен интервалом 60 s; ошибка остаётся в голосовой диагностике и не становится executor.error.

Один устойчивый source содержит domain+config_entry_id+process_id. Название и помещение передаются отдельно. Замена оборудования в существующей записи не требует нового источника в центре. Каждая загрузка runtime создаёт новый producer_session; после reload старые INFO не восстанавливаются. Перезагрузка центра вызывает регистрацию актуального snapshot через ready. Сохраняется только режим обслуживания, не история речи.

В диагностике `voice` есть версия протокола, process_id, состояние регистрации, maintenance, разрешения уровней и список активных ключей. Аппаратные entity_id, персональный MQTT-топик, session IDs и название помещения туда не копируются.

## Проверки и незавершённая приёмка

2026-09-29: **149 тестов PASS — 73 автономных и 76 HA**, из них 16 новых методов в `tests/ha/test_voice.py`. Hassfest: 1 интеграция, 0 invalid. Локальная HA 2026.9.2 / Python 3.14.5, целевая установка HA 2026.9.3 ещё не обновлялась.

Фиктивный получатель в HA-тестах проверяет клиентские вызовы: загрузка в обоих порядках, snapshot/продление, повторное согласование, timeout/rejection, смена center/producer session, возрастающие revision, явное resolved, восстановление после lease expiry той же сессией, отсутствие старых INFO, сохранение обслуживания и независимость исполнительного контура. Он не является реализацией Home Control и не доказывает воспроизведение речи.

Следующий этап в задаче Home Control: реализовать согласованный приёмник, проверить его схемы и очереди, затем совместно проверить регистрацию SRCC, каждый разрешённый уровень, обслуживание, ночную тишину, отсутствие маршрута и reload обеих интеграций. До этого end-to-end совместимость не заявляется. Эта задача не устанавливает SRCC на рабочую HA и не публикует релиз.
